# 📚 知识库问答系统（RAG）

基于 **RAG（检索增强生成）** 的知识库问答系统：把本地文档导入向量库，用自然语言提问，系统检索相关内容并生成回答，**支持来源追溯、混合检索与效果评测**。

提供**命令行**与 **HTTP 接口（FastAPI）** 两种使用方式，并附带 Dockerfile 容器化配置（本地未做容器实测）。

## ✨ 功能特点

- **本地私有化部署**：模型全部跑在本机（Ollama），数据不出本地，无 API 费用
- **多格式文档支持**：支持 `.txt` / `.md` / `.pdf`，含 PDF 文本提取与清洗流水线
- **真实工业手册验证**：知识库含西门子 S7-1200 系统手册（329 页）+ 台达 DVP 系列
  手册（976 页），检索指标是在 **2822 块真实数据**上标定的，不是小样例
- **混合检索**：向量检索（语义）+ BM25 关键词检索，RRF 融合 —— 小库 Hit@3 0.86 → 1.00，
  真实库 **0.93**
- **Agent 模式**：模型自主决定"直接回答"还是"调用工具"（ReAct 循环），可连续调用多个工具
- **效果可评测**：内置 19 条评测集与三个量化指标，阈值靠扫描实测选出来，不靠猜
- **提取质量可检查**：`check_extract.py` 一眼看出清洗删了多少、有没有误删正文、哪些页是扫描件
- **防幻觉回答**：提示词约束仅基于检索材料回答；库外问题明确返回"未找到"，且**来源同步清空**，不误导用户
- **来源追溯**：每条回答标注信息来源文档，便于核查
- **可观测**：每次问答记入 SQLite（问题 / 来源 / 耗时 / 是否拒答），支持回放 bad case 与统计拒答率
- **配置外置**：模型、阈值、端口走 `.env`，换环境不改代码
- **自动化测试**：36 个 pytest 用例，覆盖真实踩过的 bug（附 1 个 xfail 标记已知限制）
- **HTTP 接口**：FastAPI 提供 GET/POST 问答接口与统计接口，自动生成交互式 API 文档

## 🏗 项目结构（分层）

```
入口层    rag.py（命令行，支持 --agent）  api.py（HTTP 接口）  try_qa.py（调试）  eval_retrieval.py（评测）
                        ↓  共用
Agent 层  agent_core.py    工具注册表 + ReAct 循环（模型自主决定调哪个工具）
                        ↓  调用
核心层    qa_core.py        检索 + 组装材料 + 生成回答 + 来源追溯
                        ↓
检索层    hybrid_retriever.py   向量检索 + BM25 → RRF 融合
                        ↓
数据层    Chroma 向量库  |  rank_bm25 索引  |  SQLite（doc_store.py 文档元数据）  |  doc_loader.py（文档清洗）
```

**设计要点**：
- 检索与生成集中在 `qa_core.py`，多入口共用，避免"改了一处忘了另一处"
- **两个存储各司其职**：向量库负责语义检索，SQLite 负责业务元数据（文档列表 / 块数 / 统计）与**问答历史**
- Agent 的工具**只提供素材不做生成**——工具做"信息获取"，Agent 做"决策与回答"
- **配置集中在 `config.py`**：模型名、阈值、端口走环境变量 / `.env`，换环境不用改代码

```bash
pip install -r requirements.txt
```

```bash

ollama pull qwen2.5:3b  # 问答模型
```

把 `.txt` / `.md` / `.pdf` 文档放入 `knowledge/` 文件夹（PDF 会自动提取文本并清洗）。

### 4h. 问答历史与统计（可观测性）

每次问答都会写一条记录到 SQLite 的 `query_log` 表：**问题、回答、来源、
命中的块数、检索耗时、端到端耗时、是否拒答**。

```bash
# 接口版启动后
GET /stats      # 知识库统计 + 问答历史统计（总次数 / 拒答率 / 平均耗时）
GET /history    # 最近 10 条问答记录
```

输出示例：

```json
{
  "knowledge_base": { "doc_count": 3, "chunk_count": 18, "total_chars": 1621 },
  "queries": { "total": 2, "refused": 1, "refusal_rate": 0.5, "avg_total_ms": 12314 }
}
```

为什么要有这张表：它是**「收集 bad case → 改进检索 → 用评测集验证」**这个闭环的入口。
线上答错时不用靠回忆，把那条记录拎出来就能判断问题出在哪一层：

| 现象 | 说明 |
|---|---|
| `hit_count` 低 | 检索没召回 → 切块 / 阈值 / 检索策略的问题 |
| `hit_count` 正常但 `refused=1` | 模型判断材料里没有 → 提示词或模型能力的问题 |
| `retrieval_ms` 远大于 `total_ms` | 检索拖慢了响应 → 索引或 BM25 的问题 |

拒答率也能直接从这里算出来，不必另跑评测集。

## 📊 检索效果评测（评测驱动调优）

内置 **17 条评测集**（14 条有答案 + 3 条库外问题），量化三个指标：

| 指标 | 含义 |
|---|---|
| 命中率 Hit@3 | 期望来源出现在前 3 条结果中的比例 |
| Top1 准确率 | 期望来源排在第 1 位的比例 |
| 拒答率 | 库外问题正确返回空结果的比例 |

跑法：`python eval_retrieval.py`

### 三种方案的实测对比

**小示例库（18 块，2026-09）** —— 最初的对比实验：

| 方案 | Hit@3 | Top1 | 拒答率 | 结论 |
|---|---|---|---|---|
| 纯向量检索 + 相似度阈值 | 0.86 | 0.86 | 0.67 | 基线；漏检专业术语类提问 |
| **混合检索（向量 + BM25，RRF 融合）** | **1.00** | **1.00** | 0.67 | ✅ 最终采用 |
| 混合检索 + LLM 重排序 | 0.43 | 0.43 | 1.00 | ❌ 放弃（见下） |

> ⚠️ 上表的 1.00 是在 3 个文档、1621 字的小库上得到的，**不能当真实水平看**。
> 换成两本真实工业手册（2822 块）后重新标定，结果是
> **Hit@3 0.93 / Top1 0.93 / 拒答率 1.00**，详见下方
> 「10. 换成真实工业手册后，三个假设同时被打碎」。

### 实验记录：一次失败的优化尝试

在混合检索之上增加"LLM 重排序"（两阶段检索：粗排召回 → 模型精排），期望提升精确度，
**实测反而让命中率从 1.00 掉到 0.43**。三轮诊断过程：

1. **打分式提示词**（让模型给每条候选打 0-2 分）→ Hit@3 降至 **0.71**。
   诊断发现 3B 模型打分不可靠：对明显相关的内容打 0 分、对无关内容打 1 分。
2. **选择式提示词**（让模型选出"能回答问题的候选编号"）→ Hit@3 降至 **0.36**。
   诊断发现模型对明明包含答案的候选仍回答"无"，判断过度保守。
3. **放开候选片段截断**（原先把候选截断到 80 字符，而答案在块的后半段，模型看不到）
   → 放开到 200 字符后回升至 **0.43**，但仍远低于混合检索。

**结论**：3B 级小模型无法胜任细粒度的相关性判断任务。生产环境应使用**专门训练的
reranker 模型**（cross-encoder，如 bge-reranker 系列），而不是通用小模型。

**这次实验最大的价值**：如果没有评测集，很可能误以为"加了 rerank 更高级所以更好"，
从而交付一个效果更差的系统。**评测集是防止"凭感觉优化"的唯一手段。**

## 💡 关键技术实践（踩坑记录）

### 1. 嵌入模型选型：nomic-embed-text → bge-m3

初始使用 `nomic-embed-text`，实测发现中文场景语义区分度不足——例如"上班时间灵活吗"无法正确命中"弹性工作制"，多个文档的 distance 值挤在一起（0.17~0.38）难以区分。换用 `bge-m3` 后检索命中率显著提升，distance 区分度明显改善。

### 2. 相似度阈值调优：解决"检索到但不相关"

**问题**：Chroma 的 `query(n_results=3)` 总会返回 3 个"最接近"的块，即使问题与知识库完全无关（如"公司食堂吃什么"），也会返回结果并标注来源，误导用户。

**诊断**：打印实际 distance 值对比——

| 问题 | distance | 相关性 |
|---|---|---|
| 什么是RAG（相关） | 0.39 | ✅ |
| 公司食堂吃什么（无关） | 0.59 | ❌ |

**解决**：取中间值设阈值 `distance < 0.5` 判定为相关，否则返回"未找到"。修复后无关问题 `sources` 正确返回空列表。

### 3. 防幻觉提示词设计

提示词中明确约束："请只基于下面的材料回答问题，如果材料中没有相关信息，就说'知识库中没有找到相关信息'"，并在检索结果为空时直接短路返回，不调用模型。

### 4. metadata 来源追溯

存入向量库时为每个块附带 `metadata={"source": 文件名}`，检索后取出该字段展示给用户，实现答案可溯源。

### 5. PDF 文本清洗流水线

PDF 直接用 `pypdf` 提取出来的文本**很脏**，必须清洗才能入库，否则影响检索匹配。处理的五类问题：

| 脏点 | 现象 | 解决 |
|---|---|---|
| 页眉页脚 | 每页重复出现，是噪声 | 统计"行出现在几页"，≥2 页的判为页眉页脚删除 |
| **带页码的页脚** | "第 1 页"/"第 2 页"字符串不同，无法判为重复 | **只归一化页码模式**（`第X页` / `Page X`），再统计 |
| 断行 | PDF 换行是排版需要，句子被硬切断 | 缓冲区算法：按标点/标题/列表符号判断该断还是该接 |
| 多余空格、连字字符 | 字间插空格、`\ufb03` 等 | 正则压缩空格 + 字符替换 |
| 扫描件 | 文字层为空，提取不到内容 | 检测"平均每页字符数 < 20"并告警，提示需 OCR |

**踩坑记录（三轮迭代）**：

1. 最初只按"完全相同的行"识别页眉页脚 → **带页码的页脚全部漏掉**（"第 1 页"和"第 2 页"字符串不同）。
2. 改成"把**所有数字**替换成 `#` 后再比较" → 页脚能识别了，但引入更严重的问题：
   真实手册的参数表里同一个参数名在不同页面数值不同，例如"工作电压：DC 24V"与"DC 12V"
   归一化后变成同一个 key，**被误判为重复行而整行删除**——正好删掉用户最想查的内容。
   （用两页参数表复现时，整页内容被清空。）
3. 最终改为**只归一化页码模式**（正则 `第\s*\d+\s*页|Page\s*\d+|^\s*\d+\s*$`），
   既解决了页码页脚，又不会误伤正文数字。

**教训**：归一化/模糊匹配的范围要尽可能**小**——为了修一个小问题而放宽匹配条件，
可能引入更大的数据损失。修复后补充了"参数表不被误删"的回归测试用例。

### 6. 答案解析与来源不一致

**问题**：模型基于材料判断"没有相关信息"时，接口仍会返回检索到的来源列表，用户看到
"知识库中没有找到" 却列着两个文档，容易误解。

**解决**：答案解析为"未找到"时同步清空 `sources`。检索为空时也直接短路返回，不调用模型。

**踩坑 1：用短词表判定拒答，误伤正常回答**

最初判据是 `any(marker in answer for marker in ("没有找到", "没有相关", "未找到", "无法回答", "无法确定"))`，
结果把 `"dict.get() 可以避免'没有找到键'的报错"` 这类**正常回答**也判成拒答，来源被错误清空。
根因是**片段越短越容易误伤**——"没有找到"这种 4 字组合在中文里太常见。

改为**匹配完整拒答话术**（提示词里已强制模型使用固定说法），先做标点/空白归一化再匹配：

| 回答 | 旧短词表 | 完整话术匹配 |
|---|---|---|
| 「…避免'没有找到键'的报错」 | 拒答 ❌ 误判 | 正常 ✅ |
| 「知识库中没有找到相关信息」 | 拒答 ✅ | 拒答 ✅ |

**关键细节**：模型实测会丢掉句末标点（输出 `知识库中没有找到相关信息`，而不是带「。」的原句），
所以"精确等于固定话术"反而会**漏判**——匹配前必须归一化。

**残留风险**：窄匹配的代价是反向的——模型若改说"材料中未提及"这类别的措辞就判不出来。
彻底方案是让模型输出 JSON 用字段判断，但实测 3B 模型会把字段填反（见上文「实验记录」），
所以当前方案是在现有模型能力下的取舍。已补 `test_qa_core.py`（10 条用例）锁住这两类边界。

**踩坑 2：两个入口各写一遍**

这类问题属于"接口输出的一致性"——功能能跑通，但用户体验矛盾。类似的还有：
两个入口（命令行 / 接口）各自实现了一遍检索逻辑，导致"优化只改了一处"（后来重构为
共用的 `qa_core.py` 解决）。

### 7. 模型服务的容错（超时 / 状态码 / 503）

**问题**：最初的模型调用是这样的——
```python
resp = requests.post(url, json=payload)          # ❌ 没有超时
return resp.json()["message"]["content"]         # ❌ 没检查状态码
```
两个后果：
1. **没有 timeout**：Ollama 卡住时请求会**永久挂起**，占住线程不释放
2. **不检查状态码**：服务返回错误时，会在 `resp.json()` 抛一个和真实原因无关的解析异常

**解决**：
- 请求加 `timeout=120`
- 显式检查 `status_code != 200`，把响应体前 200 字符带进错误信息
- 定义 `ModelServiceError`，区分"连接失败 / 超时 / 状态错误 / 返回格式异常"四种情况
- 接口层用 `@app.exception_handler` 把它映射成 **HTTP 503**（Service Unavailable）
  —— 而不是 500 崩溃，监控系统能识别并告警
- 命令行版捕获后提示并**继续等下一个问题**，不让程序退出

**验证方式**：把 `OLLAMA_URL` 指向一个不存在的端口启动服务，请求 `/ask` 应返回：
```json
{"error": "模型服务暂不可用", "detail": "无法连接模型服务，请确认 Ollama 已启动"}
```
（模型地址支持用环境变量 `OLLAMA_URL` 覆盖——这也解决了"容器里连不到宿主机 Ollama"的问题。）

### 8. Dockerfile 漏拷模块（容器启动即崩）

**问题**：Dockerfile 里逐个 `COPY api.py .` / `COPY rag.py .`，**漏掉了
`qa_core.py`、`hybrid_retriever.py`、`doc_loader.py`** —— 容器启动时 `import qa_core`
直接 `ModuleNotFoundError`，服务根本起不来。

**根因**：**"逐个列举文件"这种写法，新增模块时必然会忘**（这类问题叫"清单不同步"）。

**解决**：
```dockerfile
COPY . .          # 一次性拷全部，从根上消除"忘记加文件"
```
配合 `.dockerignore` 排除不需要进镜像的东西（`chroma_db/`、`*.db`、`__pycache__/`、
`.git/`、`README.md`）。

**教训**：**能用"整目录拷贝 + 排除清单"就不要用"逐个列举"**——前者漏了只是多拷，
后者漏了直接崩。

### 9. 从模型输出提取 JSON：正则贪婪匹配的坑

**问题**：用一个正则从模型输出里抠 JSON：
```python
re.search(r"\{.*\}", text, re.DOTALL)      # ❌ 贪婪匹配
```
`.*` 是**贪婪**的，会从**第一个 `{`** 一路吃到**最后一个 `}`**。当模型一次输出多个
JSON（比如既有工具调用又有回答）时，两段会被黏在一起 → `json.loads` 报
`Extra data` 解析失败。

**直觉解法（更糟）**：改成非贪婪 `.*?`
```python
re.search(r"\{.*?\}", text, re.DOTALL)     # ❌ 遇到【嵌套】JSON 会提前截断
```
非贪婪匹配到**第一个 `}`** 就停。但像 `{"action":"tool","args":{"device_id":"x"}}`
这种**嵌套**结构，第一个 `}` 是**内层**的 → 截断出半个 JSON → 同样解析失败。
实测非贪婪在三种场景下 **0/3 全败**。

**解决：括号配平（数深度）**
```python
for m in re.finditer(r"\{", text):         # 从每个 { 开始试
    depth = 0
    for i in range(m.start(), len(text)):
        if text[i] == "{":   depth += 1
        elif text[i] == "}":
            depth -= 1
            if depth == 0:                 # 深度归零 = 配对的 } 找到了
                return json.loads(text[m.start():i + 1])
```

| 场景 | 贪婪 `.*` | 非贪婪 `.*?` | **括号配平** |
|---|---|---|---|
| 多个 JSON 对象 | ❌ | ❌ | ✅ |
| 嵌套 JSON | ✅ | ❌ | ✅ |
| 夹带解释文字 | ✅ | ❌ | ✅ |

**教训**：**正则擅长"字符模式"，不擅长"嵌套结构"**。JSON / HTML / 代码这类有配对
结构的内容，应该**按结构解析**（数括号、用真正的解析器），而不是靠正则硬凑。
（可运行 `demo_json_extract.py` 复现三种方式的差异。）

### 10. 换成真实工业手册后，三个假设同时被打碎

前面所有调优都建立在 3 个文档、1621 字的"示例知识库"上。往 `knowledge/`
放进两本真实的厂家手册之后（西门子 S7-1200 系统手册 329 页、台达 DVP 系列
976 页），**三个原本"验证过"的假设同时失效**：

| 假设 | 真实数据下的结果 |
|---|---|
| 页眉页脚：某行重复 ≥2 页就删 | **删掉了 30% 的正文** |
| 嵌入：一次性 `collection.add()` | **ReadTimeout，且旧库已被删空** |
| 拒答：向量超标 且 BM25 为 0 | **拒答率从 0.67 掉到 0.00** |

#### 10.1 页眉页脚规则把正文当页眉删了

原规则：某行在 ≥2 个页面出现 → 当页眉删掉。

```
台达 DVP（976 页）：删掉 30.8% 正文
  误删 "3. 指令集"(318页)、"運算元"(239页，表格表头)、"X0"(321页，指令操作数)
西门子（329 页）：删掉 32.1% 正文
  误删 "技术规范"(97页)、"4.4 程序结构"(48页)
```

**根因**：章节标题、表格表头、章节页眉**天生就在大量页面重复**，和真页眉
页脚长得一模一样，光看"重复次数"区分不了。

**修法**：加"出现页数占比"门槛。用一个诊断脚本量出这些行到底出现在多少页：

```
真页眉 "S7-1200 G2 可编程逻辑控制器"  → 99.7%  → 删
页码 / 版本页脚                      → 92% / 96% → 删
章节标题 "技术规范"                   → 29.5%  → 留
表格表头 "運算元"                     → 24.5%  → 留
正文     "X0"                        → 32.9%  → 留
```

分得很开，取 **50%** 作门槛（`PDF_REPEAT_MIN_RATIO`）。修后删除率：
西门子 32.1% → **6.0%**，台达 30.8% → **0%**。

顺带一个试过但放弃的方案：用"行在页面里的位置"判断（真页眉固定在首尾）。
**pypdf 的 `extract_text()` 按内容流顺序输出、不是视觉顺序**，实测同一行
页眉在 329 页里有 149 页被排到了"中间"，位置信号不可靠 —— 比例信号才是干净的。

**取舍**：台达那本页眉最高才占 35.5%，够不到 50%，所以**一行都没删**（漏删）。
没去调低阈值，因为台达 `X0`（正文）是 32.9%、`#`（页码）35.5%，**只差 2.6 个
百分点**，调低就会重新误删正文。漏删页眉 = 多几行噪声；误删正文 = 内容永久
丢失。两个代价不对称，所以选保守。

#### 10.2 一次性嵌入全部块 → 超时 + 旧库被删空

`collection.add(documents=全部块)` 会让 chroma 把**所有文本塞进一个**
embedding 请求。2822 块的单请求要 6 分钟以上，直接 `ReadTimeout`。

更糟的是原代码是"先 `delete_collection` 再建新的"——**非原子**。嵌入失败时
旧库已经删光了，而报错信息里只写"超时"，完全看不出库已经空了。

**修法两条**：
1. **分批嵌入**（`EMBED_BATCH_SIZE=64`），带动进度条和 ETA
2. **先把 embedding 全部算完，再删旧库** —— 算的过程中出错，旧库原样保留；
   算完后只是纯写入，很快，不会再碰模型

实测速率：174 ms/块（2822 块约 8 分钟）。

#### 10.3 拒答规则在大库上完全失效

原规则：`向量最优距离 > 阈值 且 BM25 最高分 == 0` → 拒答。

上了 2822 块的库，**库外问题一条都拒不掉**。量出来的 BM25 分数：

```
库外："怎么用 Excel 做数据透视表"  BM25 = 18.078   ← 因为命中"数据"
库外："帮我写一首诗"              BM25 = 10.623
库内："PROFINET 通信怎么配置"      BM25 = 11.823   ← 库内反而更低
```

**库一大，几乎任何中文问题都能在某个块里命中几个常用词**，所以 `BM25 == 0`
永远不成立 —— 整条规则形同虚设。

**修法**：**BM25 只负责召回与排序，该不该拒答只看向量距离。**

阈值也不是原来的 0.5 了。库变大后所有距离整体前移，用 19 条评测问题扫了一遍：

```
阈值   误拒  误答  总错误
0.41     2     0     2
0.44     1     0     1   ← 最优
0.46     1     1     2   ← 库外开始漏
```

`0.44~0.45` 是稳定区间，取 0.44。修后拒答率 **0.00 → 1.00**。

#### 10.4 评测集本身太脆

加进真手册后 Hit@3 从 1.00 掉到 0.79，但一看明细：

```
❌ 数字量输入有多少点   期望 示例.pdf   实际 ['S7-1200系统手册_西门子.pdf']
```

**答案是对的、来源更权威，只是文件名对不上。** 评测用精确文件名做断言，
文档一重叠就全变假阴性。改成"命中任一可接受来源"（`S7_SOURCES`）即可。

**教训：评测断言要盯"语义上是否正确"，不要盯"实现细节"。**

#### 10.5 还剩下一个真实失败

`Chroma 是干什么的` 的 top1 距离是 **0.558** —— 比 `红烧肉怎么做`（0.558）
还远。这条**不是阈值问题**：`大模型笔记.txt` 只有 503 字，对 Chroma 压根
没讲清楚，检索确实找不到像样的匹配。拒掉它是合理的。

要修只能两条路：补文档内容，或接 cross-encoder reranker 做精排判相关。

#### 10.6 最隐蔽的一个：近似检索把真正的最近邻漏掉了

把台达手册也加进来之后（976 页，库涨到 **11048 块**），`RAG 是什么` 突然检索不到了。
第一反应是"大文档把小笔记淹没了"—— **这个解释是错的**，是查下去才发现的。

排查过程（每一步都是可复现的）：

```
1. 先怀疑是 HNSW 近似检索：把 n_results 从 3 → 10 → 50 → 200 → 1000
   结果：n=10/50/200 返回的最近距离都是 0.6499，n=1000 才变成 0.3844
   → 说明真近邻存在，只是取不到

2. 再怀疑嵌入不可复现：同一段文本单独调用 3 次
   结果：平方距离 = 0.00000000 —— 完全确定性

3. 暴力全量精确检索（11048 × 1024 全算一遍）作对照：
   真正的 top1 = 0.3844  [大模型笔记.txt]
   Chroma 返回 = 0.6499  [S7-1200系统手册]
   → 确实是检索漏了，不是数据问题

4. 顺便确认了距离的度量口径：
   库内向量与查询向量范数都是 1.000000，
   Chroma 返回的 distance 精确等于 1 - cos（0.649930 完全吻合）
```

**结论：Chroma 默认的 HNSW `search_ef`（搜索候选池）太小。**
小库（2822 块）时候选池足够，碰巧能撞到真近邻；涨到 11048 块后，真近邻被埋在
图的深处，默认广度探不到 —— 表现出来就是"越相关的文档反而检索不到"。

**修法**：建 collection 时显式设置 HNSW 参数。

```python
metadata={
    "hnsw:space": "cosine",
    "hnsw:search_ef": 500,          # 搜索广度（默认 100，大库上不够）
    "hnsw:construction_ef": 400,    # 建图质量
    "hnsw:M": 32,                   # 每个节点的连接数
}
```

修后 `n=10` 就能找回 0.3844，**Hit@3 从 0.86 恢复到 0.93**。

> **这个坑最值得记的一点**：它不会报错，只会"悄悄地检索不到最相关的东西"。
> 而且它**只在大规模数据上出现**——小样例永远测不出来。
> 判断方法就是暴力全量检索做对照：这个规模（1 万块 × 1024 维）用 numpy
> 全算一遍只要几毫秒，完全负担得起，非常适合当"真值"来校验索引。

#### 这一轮的量化结果

| 指标 | 小示例库（18 块） | 西门子手册（2822 块） | **两本手册（11048 块）** |
|---|---|---|---|
| Hit@3 | 1.00 | 0.93 | **0.93** |
| Top1 | 1.00 | 0.93 | **0.93** |
| 拒答率 | 0.67 | 1.00 | **1.00** |
| 测试用例 | 19 | 35（+1 xfail） | **35（+1 xfail）** |
| 重建耗时 | 秒级 | 8 分钟 | **2.5 分钟（命中缓存）** |

**指标不是"变好"了，是"变真"了。** 小库上的 1.00 是靠 3 个文档的运气；
现在 13/14 是在 11048 块真实手册上的成绩，而且清楚知道剩下那 1 条为什么失败。

## 🔜 后续优化方向

- **接 cross-encoder reranker**（bge-reranker-base）替代"距离阈值"做相关判定 ——
  当前 0.44 的阈值余量很薄（库内最高 0.433、库外最低 0.453），靠 reranker 更稳
- **补文档覆盖**：`Chroma 是干什么的` 检索不到（top1 距离 0.558），原因是
  `大模型笔记.txt` 对该概念讲得太少
- 扫描件 OCR 支持（PaddleOCR），覆盖图片型 PDF
- Word（.docx）文档解析，以及表格结构化提取
- 优化分块策略（当前按固定字数切，"数字量输入：14 点"和"数字量输出：10 点"被切散）
- 支持多轮对话（带历史上下文的追问）以及用户反馈闭环
- 命令行暂不支持列出/删除单个文档（`doc_store` 已有 `list_documents` / `delete_document`，缺入口）
- 问答历史目前只有接口和 SQLite 原文，没有可视化面板

## ✅ 已完成的关键改进

- 嵌入模型选型：nomic-embed-text → bge-m3（中文检索效果显著提升）
- 相似度阈值调优：基于实测 distance 数据确定阈值
- PDF 文档支持 + 文本清洗流水线
- 混合检索（向量 + BM25 + RRF）：命中率 0.86 → 1.00
- 检索效果评测集（17 条）与量化指标
- 抽取公共核心模块 `qa_core.py`，命令行 / 接口 / 评测共用同一实现
- 文档元数据管理模块 `doc_store.py`（SQLite：列表 / 统计 / 级联删除），并在建库时同步写入
- **Agent 模式**（`agent_core.py`）：ReAct 循环 + 工具注册表，模型自主决定调用 RAG / SQL 工具
- **模型服务容错**：请求超时 + 状态码检查 + `ModelServiceError` → 接口返回 503
- **Docker 构建修正**：`COPY . .` + `.dockerignore`，消除"漏拷模块"问题
- **健壮的 JSON 提取**：从正则贪婪匹配改为"括号配平"，正确处理嵌套与多对象输出
- **配置外置**：`config.py` + `.env.example`，模型/阈值/端口不再散落在各模块里
- **可观测性**：`query_log` 表记录每次问答（来源 / 耗时 / 是否拒答），`/stats`、`/history` 接口直接查
- **测试工程化**：两套回归测试改为 pytest 用例（**19 passed + 1 xfailed**），`pytest -v` 一条命令可见
- **接入真实工业手册**：西门子 S7-1200（329 页）+ 台达 DVP（976 页），库涨到 **11048 块**
- **页眉判定加比例门槛**：修复真实手册上"删掉 30% 正文"的误删（`PDF_REPEAT_MIN_RATIO`）
- **建库健壮性**：分批嵌入 + 分批写入（Chroma 单次上限 5461）+ embedding 落盘缓存，重建 32 分钟 → 2.5 分钟
- **HNSW 参数显式化**：修复大库上"近似检索漏掉真近邻"（`search_ef` 默认太小），Hit@3 0.86 → 0.93
- **阈值标定工具**：`tune_threshold.py`，库一变一条命令重新标定 `MAX_DISTANCE`
